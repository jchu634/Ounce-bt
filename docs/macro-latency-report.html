01What was tested

The tests examined whether Ounce-bt's macro waits match the requested durations, whether repeated inputs remain consistent, and how long an input takes to produce a detectable response in the Switch video feed.

  • Software timing: 230 local press/neutral cycles at 1, 5, 10, 16.667, 33.333, 50, 100, 250 and 500 ms.
  • Hardware timing: 60 directional presses on the Switch Controllers menu across two runs. Each run used ten presses at each of 50, 100 and 250 ms, followed by 600 ms neutral.
  • Captured response: first detected highlight movement, measured using the corrected detector in the second run.
  • Connection: saved-controller reconnect and earlier disconnects after leaving Change Grip/Order.

Environment: Windows · Python 3.14.5 · production macro player and report loop · configured macro rate 120 Hz and report-loop target 132 Hz · Elgato Game Capture 4K60 Pro MK.2 PCIe.

02Methodology

Where the clocks were placed

How hold durations were measured

All event timestamps used the same machine's perf_counter clock. The hardware wrapper recorded state changes immediately before Bluetooth report submission. The local test used the production macro player, report loop and controller protocol with a timestamped substitute channel.

Capture and movement detection

The capture card supplied 1920 × 1080 video at 60 fps. FFmpeg scaled it to 480 × 270 RGB. Python timestamped each complete frame on arrival. The corrected detector tracked the highlight's chroma-weighted vertical centre across the menu and required movement of more than eight scaled pixels in the input direction within a rolling 55 ms window. It matched the first movement within 400 ms of each press.

Interpretation limit. The response measurement includes Switch/menu processing, animation, HDMI, capture buffering, FFmpeg and pipe delivery. Frame arrivals were uneven, with detection-frame gaps reaching about 32 ms. Treat the result as roughly 0.12 seconds through this measurement path, rather than isolated Bluetooth latency or calibrated display latency.
Connection history and detector corrections

Earlier pairing attempts succeeded, but the Switch disconnected after leaving Change Grip/Order with either A or B. Later, the measurement app was started once and a saved reconnect completed. An early second reconnect request was rejected because the first connection was still active and handshaking. The completed connection survived both test runs.

Directional holds of 250 ms triggered the menu's key repeat. The first detector watched only the top row and sometimes timed the second repeated movement. Those run-1 latency results at 250 ms are invalid for first-response latency. Run 2 tracked all menu rows instead.

A simple threshold also mistook gradual border-colour drift for a 375 ms response to one unmatched press. The corrected movement detector rejected that false positive. Raw and superseded data were retained.

One 50 ms UP press produced no detected movement. Its submitted report hold error was −6.52 ms; the highlight stayed on Search for Controllers, then the next DOWN moved to How to Pair Controllers.

The first run detected all ten 50 ms presses, giving 19 visible responses across twenty 50 ms trials. All tested 100 and 250 ms presses produced movement. These small samples are observations, not a long-run reliability estimate. The missing response does not establish whether Bluetooth delivery, Switch input sampling or menu handling caused it.

Why captured response latency is separate from hold error

The programmed wait controls the time between press and release. It does not specify how long the Switch and capture system should take to display a response. Subtracting a 50, 100 or 250 ms hold from response-onset latency would compare different quantities. Captured response latency remains in the raw evidence; it is not used for these target-deviation distributions.

04Conclusions

  1. Delays are approximate. Average report holds were close to their settings, while individual durations varied by several milliseconds. Repeated relative waits also accumulated drift.
  2. The captured menu response was about 0.12 seconds. This applies to the tested acquisition and detection path. It should not be read as the Switch's Bluetooth latency alone.
  3. Short inputs were less dependable. The local report loop lost or merged many 1–5 ms pulses. One of twenty 50 ms hardware presses produced no visible movement. These tests do not establish a universally safe minimum hold.
  4. Reconnect enabled the completed tests. The successful session survived both runs. The reported GUI first-connection/second-connection bug and its cause remain unverified.
Verdict: NOT VERIFIED

Exact timing and perfect consistency were not demonstrated. No application changes or candidate fixes were tested, and no product timing tolerance had been specified. This verdict addresses the strict claim of exact matching and perfect delivery.

Follow-up work suggested by the evidence

Investigate preserving short state transitions in the report consumer and scheduling waits against a shared timeline. Test any change against the current implementation with the same macros and acquisition settings. To separate Bluetooth latency from capture latency, add independent timestamps or a calibrated external reference.
